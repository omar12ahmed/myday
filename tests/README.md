Automated checks that open MyDay in a headless Chrome and use it the way you would: tapping

## Run them

From the `myday-site` folder:

```sh
tests/run.sh                  # everything (about 22–37 minutes at 1.40.0)
tests/run.sh storage          # one suite (under a minute)
tests/run.sh storage today    # several suites
tests/run.sh app-storage app-today app-calendar-pay app-finance app-inbox app-tasks app-patterns patterns-rules app-study app-workout app-food app-final app-site   # the new app only (builds it first)
tests/run.sh sync-db app-sync # cloud sync only
tests/run.sh ai-rules ai-server app-ai   # AI help only
tests/run.sh study-guided-rules app-study-reset   # Guided Study rules and local two-device reset
```

You need Google Chrome, Node.js 22 or newer, and Python 3. If Chrome is somewhere unusual, set
`CHROME=/path/to/chrome`. If the default ports are in use, set `MYDAY_CDP_PORT`, `MYDAY_HTTP_PORT` or
`MYDAY_LS_PORT`.

A few checks need the internet: one real gov.uk bank-holiday request, one real TheMealDB request, and
`npx live-server` for the Live Server check. Everything else uses made-up responses, so offline those
few will fail and the rest still run.

**At another time of day.** Most browser suites set their own date and hour (`openAt` in `cdp.js`, in Los
Angeles time), so when you run them doesn't matter. The suites that use the real clock (app-ai, app-sync and the
rules suites) can be run as if it were another local time: give Node and the two-device kit the same time zone.
For example, when it's 16:30 UTC, `TZ=Etc/GMT-8 MYDAY_TEST_TZ=Etc/GMT-8 tests/run.sh app-ai` runs just after
midnight (`Etc/GMT-8` is UTC+8). `MYDAY_TEST_TZ` changes only the two-device kit (`cdp-devices.js`, Europe/London
by default). The main kit stays in Los Angeles, because its suites check dates there. Checked on 20–21 Oct 2026:
these suites pass just after midnight and just before it.

The `app-*` suites build the new app (`npm run build` in `app/`, so run `npm install` there once first) and serve it
beside the current MyDay, the way Live Server does, so the two share saved data as they do for real.
If Live Server is running, use `MYDAY_LS_PORT=5599 tests/run.sh …` so the `today` suite's Live Server check doesn't clash with it.

Run builds and build-triggering suites sequentially within one worktree. Each production build prepares shared
curriculum/audio files before Vite runs, so separate ports or output directories do not prevent build interference.
Use separate worktrees and distinct values for all four test ports if concurrent runs are necessary.

The sync suites use `@electric-sql/pglite`, a development package of the new app (so `npm install` in `app/` first).
`app-sync` and `app-ai` build a copy of the app with `VITE_SUPABASE_URL` pointing at the stand-in; other app copies
are built without sync settings, even if production environment files have them. The stand-in can also run on its own:
`node tests/supabase-standin.js 54329`.

**A real Supabase project** is checked with `tests/sync-live-check.js` (two disposable test accounts; see
`supabase/README.md`, step 5). It isn't part of `run.sh`, because it needs your project and test accounts. With
`--projects-only` it checks just projects (1.12.0's migration), on test accounts that already have records from an
earlier run — only if both are disposable `@example.com` addresses, and it touches only a new project record of its own.
`--cyber-only`, `--arabic-only`, `--arabic-cards-only` and `--cyber-cards-only` do the same for the Cybersecurity,
Arabic session, Arabic revision card and Cybersecurity revision card kinds.

`fixtures/` holds two earlier versions of MyDay (as `.fixture` files, so the website doesn't serve
them as pages). The migration checks load them to make sure older saved data still comes across.

## Adding checks

Each suite is a plain script built on `cdp.js`, a small helper that drives Chrome.

- **Before fixing a bug,** add a check that fails because of it.
- **After the fix,** confirm the check passes, and that it fails if the fix is taken out.

## Split-project storage checks (1.44.0)

`project-sync` checks the real wire mapper and checked store: unknown fields, links and history, large-project
reassembly, deterministic concurrent positions, per-item and atomic batch/import refusal, quota failures and retry.
`project-sync-db` applies the upgrade to a disposable pre-upgrade database and checks exact projection, original
recovery, legacy refusal, RLS, version checks, parent deletion, malformed-source rollback and large projects.
`app-sync` exercises independent project-item edits, same-item conflicts, multi-page large history, concurrent
appends and deletion/restoration between disposable browser devices. `sync-records`, `sync-db`, `storage`,
`app-storage`, `projects-rules` and `app-projects` retain the surrounding compatibility and feature coverage.
These suites use synthetic data and the local stand-in; they do not authorise or exercise a hosted migration.
